# 扫码班报分位口径核对 / 终端存档修复补传

服务分两块能力：

1. **班报分位口径核对**：班报只保留各终端在**共用、互不重叠的整数毫秒闭区间**上的
   分档笔数，以及 P50、P95、总耗时三个汇总值。用整数容量约束（**不按总笔数逐笔展开**）
   判断班报数字分别能否在两种取位口径下由**同一组读数**复算，并给出可独立复算的
   「耗时 → 笔数」见证分布。
2. **终端存档核对与流水段修复补传**：终端存档找回后，用同一份本地明细核对一个班次、
   一台终端的若干互不重叠流水号闭区间（含各段 SHA-256），列出不一致区间并签发修复编号；
   凭编号补传整段明细，摘要验过才整段替换，段外流水保留，按生效班报定档校验各档笔数。

---

## 一、终端存档核对与流水段修复补传

### 段摘要口径

每段把段内各笔按**流水号升序**拼接 UTF-8 文本（耗时为整数毫秒）：

```
流水号,耗时\n
流水号,耗时\n
...
```

对整段文本计算 SHA-256（小写十六进制）。例如两笔 `(1,120)`、`(2,130)` 的摘要输入为
`"1,120\n2,130\n"`。空段摘要即空文本的 SHA-256。

### 流程与规则

1. **核对** `POST .../reconcile`：提交一台终端一个班次的清单（互不重叠闭区间 + 各段存档
   摘要）。服务用本地明细逐段复算摘要并比对，返回每段 `match`、本地笔数、在场/缺失流水号；
   不一致段各签发一个 `repair_id`，并记录**核对时刻的段摘要快照**。
2. **补传** `POST /repairs/{repair_id}/complete`：只传段内每笔的 `seq` 与 `value_ms`
   （不传分档，按生效班报闭区间自动定档）。判定顺序：
   - 段内流水号不重复、且都落在该段闭区间内，否则整批退回（422，不改库）；
   - 独立复算补传内容摘要，**与存档一致才允许替换**，否则退回（422，不改库）；
   - 摘要验过后看库内现状：已与存档相符 → 返回 `already_complete`（不改明细）；
     仍不符且相对核对时刻快照**已变动** → 退回（409，需重新核对）；
   - 否则**整段替换**：删除该终端段内闭区间中的全部旧流水（**含段内多出的旧号**），
     插入补传明细；**段外流水（含段外补录）原样保留**。
3. **按生效班报定档校验**：替换后该终端每笔耗时须落在所属分档闭区间，且各档笔数不得超过
   班报声明；任一不满足整次回滚（422，不改库）。
4. **普通补交与修复交错**：后写一方在先写入的结果上做容量/定档校验，保留本次范围外流水；
   普通补交改动了待修段且仍不符时，修复会被 409 退回，重新核对后取新编号即可。
   两条写路径（普通补交、整段修复）的**读-改-写都在单个数据库事务（单次持锁）内完成**，
   后写者读到的必是先写者已提交的最新状态，因此并发下不会用旧快照覆盖（无写偏/lost
   update），也不会出现部分写入；任一校验失败随事务回滚，整次不改库。
5. **作业状态机**：`open → completed`；同一终端再次核对会把旧的 open 作业置 `superseded`
   （再用旧编号补传返回 409）。

### 新增接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/shifts/{shift_id}/terminals/{terminal_id}/reconcile` | 核对存档清单，返回逐段比对结果并为不一致段签发 `repair_id` |
| `POST` | `/repairs/{repair_id}/complete` | 凭编号补传整段：验摘要、整段替换、按班报定档校验 |
| `GET` | `/shifts/{shift_id}/repairs` | 查询某班（可加 `?terminal_id=`）修复作业状态 |

## 二、班报分位口径核对

### 口径定义

设 `p` 为分位比例、`N` 为总笔数：

| 口径 | 取排序后第几项 |
| --- | --- |
| `ceil` | 第 `⌈pN⌉` 项（至少第 1 项） |
| `floor` | 第 `⌊pN⌋` 项（至少第 1 项） |

分位数条件「第 k 项 = q」等价于双侧容量约束：

- 小于 q 的笔数 ≤ k−1
- 大于 q 的笔数 ≤ N−k

同一口径下，P50、P95、总耗时必须由**同一组读数**同时满足。

## 算法（复杂度只与分档/阈值数有关，与总笔数无关）

1. 已提交明细作为固定读数；其余读数在所属分档 `[lo, hi]` 内自由取值。
2. 最小可行和：自由读数全部取 `lo`，再按最小提价贪心把读数批量上提到分位阈值，
   修复「小于 q」容量，并复验「大于 q」容量。
3. 最大可行和：对读数取负 `x = −v` 后复用同一过程。
4. 可行总耗时是最小和与最大和之间的全部连续整数（整数容量流多面体的连通性）。
5. 班报总耗时落在区间内时，在最小和基线上用带容量余量的**批量上提**构造见证分布，
   并独立复算总和、笔数、两个分位位置后才返回。

分档笔数即使达到 10^12 也只产生常数级分组，见证分布行数远小于总笔数。

## 班报核对接口（启动后访问 `/docs` 可交互演示）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `PUT` | `/shifts/{shift_id}/report` | 登记/覆盖一班：分档、各终端档内笔数、P50/P95/总耗时 |
| `POST` | `/shifts/{shift_id}/details` | 提交/更正终端明细，主键 `(终端, 流水号)`，同号即更正 |
| `GET` | `/shifts/{shift_id}/details` | 查询已提交明细 |
| `POST` | `/shifts/{shift_id}/check` | 用同一份已提交明细分别核对两种口径 |
| `GET` | `/health` | 健康检查 |

存档修复的三个接口见上文「一、终端存档核对与流水段修复补传」。

明细提交规则：

- 耗时必须落在该终端该分档的闭区间内，否则整批退回（422，不落库）；
- `(终端, 分档)` 必须在班报中声明，且提交后档内笔数不得超过班报笔数，否则整批退回；
- 同 `(终端, 流水号)` 再次提交即为更正，可改值也可改到本终端已声明的其他分档。

`/check` 响应中每个口径包含：`feasible`、不可行原因、可行总耗时区间
`feasible_sum_range_ms`，以及可行时的见证 `witness`（全局 `distribution`、
累计 `cumulative`、分终端 `by_terminal`、分位位置 `positions`）。

## 自测结果

- `tests/test_solver_brute.py`：对 16 组小场景（含固定明细）枚举**全部读数组合**
  逐笔排序，与求解器在每一个候选总耗时上的可行性结论逐一对照，全部一致；
  另含 10^12 笔大档测试，见证分布仍为常数行。
- `tests/test_api.py`：端到端覆盖
  1. 两种口径均可行且见证可独立复算；
  2. 越界/未声明终端/超档内容量均整批退回且不落库；
  3. 明细更正后核对结论发生变化（更正前两口径均可行，更正后 `ceil` 失效、
     `floor` 仍可行），再更正回退后结论恢复；
  4. 60 亿/40 亿/20 亿笔大档，见证为聚合分布、不逐笔展开；
  5. `/docs`、`/health` 可访问。
- `tests/test_archive_repair.py`：存档核对与修复补传端到端覆盖
  1. 段摘要手工向量对照（升序拼接 `流水号,耗时\n`、空段、乱序输入）；
  2. **整段补齐**：核对发现不一致并签发 `repair_id`，补传验摘要后整段替换，
     段内多出旧号删除、段外补录与其它段保留，替换后按班报校验各档笔数；
  3. **已补齐**：库内段已与存档相符时返回 `already_complete` 且不改明细；
  4. **变动退回**：核对后段被普通补交改动且仍不符 → 409 退回，重新核对取新编号可修；
  5. 补传自身摘要不符、段内重复/越界流水号、空补传 → 422 且整次不改库；
  6. 定档失败（耗时不落任何分档）、档内容量超限 → 整次回滚、作业仍 `open`；
  7. **普通补交与修复交错**：两个方向都验证后写方在先写结果上校验、范围外流水保留；
  8. 清单校验（重叠区间、坏摘要、空清单、未声明终端、班次不存在）；
  9. 作业状态机：未知编号 404、重复核对使旧作业 `superseded`、`completed` 行为；
  10. 稀疏段缺号识别与段内多余旧号删除、补传按耗时自动定档；
  11. **并发交错压测**：真实线程并发跑整段修复与普通补交（各数百轮），断言库始终满足
      串行化不变量——无脏写、无部分写入、各档不超容量；段外提交时修复稳定成功，
      段内提交时修复确定走"变动退回"。
